## Findings

### CICD-001 — E2E Test Project Excluded from Solution (HIGH)

The solution file `ContestJudging.slnx` includes only the unit test project
(`tests/ContestJudging.Tests/`). The E2E test project at
`tests/ContestJudging.E2ETests/` is not referenced, so
`dotnet test ContestJudging.slnx` never executes these tests. The E2E test
project uses Playwright/NUnit and tests the Blazor WASM app from the browser.

**Files**: `ContestJudging.slnx:8-10`\
**Rule violated**: CI completeness — all test projects must run in CI\
**Remediation**: Add
`<Project Path="tests/ContestJudging.E2ETests/ContestJudging.E2ETests.csproj" />`
to the `/tests/` folder in `ContestJudging.slnx`. The E2E test job may need a
separate Playwright browser installation step.

### CICD-002 — No Code Coverage Collected in CI (MEDIUM)

Both test projects reference `coverlet.collector` (v6.0.4), but the CI
`dotnet test` step runs without `--collect:"XPlat Code Coverage"` or any
`CoverletOutput` parameters. Coverage data is never generated or published.

**Files**: `.github/workflows/pipeline.yml:50`\
**Rule violated**: Test quality — coverage should be collected and tracked\
**Remediation**: Change the test step to:

```bash
dotnet test ContestJudging.slnx --configuration Release --no-build --verbosity normal --collect:"XPlat Code Coverage"
```

Optionally add a coverage report upload step (e.g., Codecov or Coveralls).

---

### CICD-003 — Floating Major-Version Action Tags (MEDIUM)

Six of seven GitHub Actions use floating major-version tags (e.g., `@v5`,
`@v6`). Only `google/osv-scanner-action` is pinned to `@v2.3.5`. Floating tags
allow automatic resolution to new minor/patch releases, introducing supply chain
risk without auditability.

**Files**: `.github/workflows/pipeline.yml:18,21,27,45,73,79,100,103,108`\
**Rule violated**: Supply chain security — actions should be pinned to commit
SHA or full semver\
**Remediation**: Pin all actions to full semver tags (e.g.,
`actions/checkout@v6.1.0`) or commit SHA digests. Enable Dependabot to keep them
updated.

---

### CICD-004 — No SAST or Static Analysis Security Scanning (HIGH)

The workflow includes only OSV-Scanner for dependency vulnerability scanning. No
CodeQL, SonarCloud, or other SAST tool is configured for the C# Blazor WASM
codebase. With `EnforceCodeStyleInBuild=true`, some Roslyn analyzer warnings
become build errors, but no dedicated security analysis runs.

**Files**: `.github/workflows/pipeline.yml:52-60`\
**Rule violated**: OWASP / DevSecOps — SAST should complement dependency
scanning\
**Remediation**: Add a CodeQL workflow (`github/codeql-action`) targeting C#.
For a Blazor WASM app, also consider JavaScript/TypeScript scanning for the
client-side runtime.

---

### CICD-005 — OSV-Scanner Uses `--allow-no-lockfiles` (LOW)

The OSV-Scanner step passes `--allow-no-lockfiles`, which skips scanning for
lockfile-backed ecosystems. This reduces accuracy because NuGet packages are
managed centrally via `Directory.Packages.props` and project-level lock files
(if present) are needed for precise dependency resolution.

**Files**: `.github/workflows/pipeline.yml:60`\
**Rule violated**: Tool configuration — scanner should use lock files for
accurate results\
**Remediation**: Remove `--allow-no-lockfiles` and ensure `packages.lock.json`
files (or `Directory.Packages.props` lock mode) are committed, or at minimum
leave the flag off and verify scans succeed.

---

### CICD-006 — `release/` Directory Committed to Repository (MEDIUM)

The `release/` directory contains a published Blazor WASM output (_framework,
brotli-compressed assets, `dotnet.js`, native SQLite libraries, `web.config`).
This is a build artifact that should be generated by CI, not tracked in version
control. It can become stale, adds binary bloat to the repo, and may conflict
with CI-published output.

**Files**: `release/` (16 files including `wwwroot/` subtree)\
**Rule violated**: Repository hygiene — build artifacts should not be committed\
**Remediation**: Add `release/` to `.gitignore` and remove it from tracking with
`git rm -r --cached release/`. The deploy job in CI already publishes to this
path.

### CICD-007 — No Dependabot Configuration (MEDIUM)

No `.github/dependabot.yml` is present. Dependencies are centrally managed via
`Directory.Packages.props`, which is a good practice, but there is no automated
mechanism to open update PRs for NuGet packages, GitHub Actions, or other
ecosystems.

**Files**: (missing) `.github/dependabot.yml`\
**Rule violated**: Dependency hygiene — automated update PRs reduce stale
dependency risk\
**Remediation**: Create `.github/dependabot.yml` with at minimum:

```yaml
version: 2
updates:
  - package-ecosystem: "nuget"
    directory: "/"
    schedule:
      interval: "weekly"
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
```

### CICD-010 — Empty `dotnet-tools.json` (INFORMATIONAL)

The local tool manifest exists but contains no tools. The CI workflow relies on
SDK-bundled commands (`dotnet format`, `dotnet test`), which is sufficient. If
additional local tools are introduced (e.g., `dotnet-coverage`,
`dotnet-outdated`), they should be registered here for reproducible builds.

**Files**: `dotnet-tools.json:4`\
**Rule violated**: Reproducibility — local tool pinning ensures consistent tool
versions\
**Remediation**: No action required currently. If new CLI tools are needed, add
them via `dotnet tool install --local`.

---

### CICD-011 — Deploy Job Redundantly Rebuilds from Source (MEDIUM)

The `deploy` job re-installs WASM tools and publishes the Blazor WASM app from
scratch, duplicating the build infrastructure already present in the
`quality-and-test` job. This wastes CI minutes (dual WASM workload install +
dual NuGet restore). With no shared artifact between jobs, there is no guarantee
the deploy job publishes the same commit that was tested.

**Files**: `.github/workflows/pipeline.yml:62-108`\
**Rule violated**: CI efficiency / integrity — deploy should use tested
artifacts\
**Remediation**: In the `quality-and-test` job, run `dotnet publish` and upload
the output as a build artifact. In the `deploy` job, download that artifact
instead of rebuilding. This ensures the tested binary is deployed and eliminates
the redundant build.
